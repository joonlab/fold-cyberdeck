# FoldLab — 폴드8 사이버덱

갤럭시 Z 폴드8에서 **맥(노트북·홈맥)을 화면째 보고 조작**하는 안드로이드 앱.
맥 쪽 짝은 이 저장소의 [`../mac`](../mac) (deckd).

> 2026-09-22 전환. 그전까지 이 앱은 무선 설치 파이프라인 검증용 데모였다(접기/펴기 dp 표시).

## 자세별 화면 구성

폴드는 **자세가 셋**이다. 같은 UI 를 세 자세에 우겨넣지 않고 갈랐다.
디자인은 이미지 생성 모델로 뽑은 키보드 목업을 보고 구현했다(목업 원본은 이 repo 에 넣지 않았다).

### 펼침 세로 (704×932dp) — 작업용
```
┌────────────────────────────┐
│  맥 화면 스트림       ~50%  │
├────────────────────────────┤
│  텔레메트리 + 칩       22dp │
├────────────────────────────┤
│  5행 키보드           ~36%  │
├────────────────────────────┤
│  트랙패드 + L/R       ~13%  │
└────────────────────────────┘
```
`KB+PAD` 칩이 **3단 순환**한다: 키보드+패드 → 패드만 → 화면만.
상황마다 원하는 비율이 달라서 고정하지 않았다.

### 펼침 가로 (932×704dp) — 보기용
스트림이 **전체화면**이고, 입력은 우하단 **플로팅 독**이다.
가로로 돌리는 행위 자체가 «크게 보겠다»는 뜻이라 **기본값은 안 가리는 것**.

- 접힘: `⌨ 입력` 손잡이만
- 펼침: 손잡이(끌면 이동·탭하면 접힘) · `FULL` · `SP< SP> MC 앱창` · 트랙패드 · L/R · 필수키 12개
- **화면 밖으로는 못 나간다.** 끌어서 내보내면 손잡이가 안 보여 되돌릴 방법이 없다(앱 재시작뿐).
  창 기준 «실제로 그려진 자리»를 재서 역산해 가두므로 앵커·safe area·자세가 무엇이든 같은 식이 맞는다.
  회전·자세 전환으로 창이 바뀌면 나가 있던 독을 도로 끌어들인다.
- `FULL`: 5행 키보드 전체를 하단에 겹쳐 띄운다
- 🚨 **높이가 짧으면(560dp 미만 = 접힘 커버 가로 475dp) 배치를 바꾼다.** 펼침 가로(704dp) 기준
  비율(0.62 + 트랙패드 86dp)을 그대로 쓰면 5행 키보드 몫이 **행당 23dp** 로 떨어져 글자가 잘린다
  (2026-09-22 실측). 짧은 화면에서는 0.80 을 쓰고 FULL 에서는 트랙패드를 빼 키보드에 준다
  (트랙패드는 `FULL` 을 끄면 바로 전면에 나온다). 자세 플래그가 아니라 **지금 높이**로 판단한다.

### 접힘 커버 (475×751dp) — 패드 우선 + 10열 압축 키보드

실측: 커버 디스플레이 **1248×1972px @ density 2.625 → 475×751dp**(상단 커서아웃 39.6dp).

**펼침용 14열을 그대로 쓸 수 없다.** 그 폭이면 키 하나가 **30.5dp(약 4.8mm)** — 터치 최소치
(Material 48dp / Apple 44pt)의 2/3 다. 그래서 커버에는 전용 **10열**(45.3dp) 키보드를 쓴다.

```
기본 (PAD)                        키보드 칩을 누르면
┌──────────────────────┐          ┌──────────────────────┐
│    맥 화면 스트림     │          │    맥 화면 스트림     │
├──────────────────────┤          ├──────────────────────┤
│ 텔레메트리 + 칩 22dp │          │ 텔레메트리 + 칩      │
├──────────────────────┤          ├──────────────────────┤
│                      │          │ q w e r t y u i o p  │ 10열
│   트랙패드 (넓게)     │          │ a s d f g h j k l ⌫  │ 45.3dp
│                      │          │ ⇧ z x c v b n m , .  │
│ [   L   ][   R   ]   │          │ 123 한영 ^ ⌥ ⌘  │ ↑  │
└──────────────────────┘          │ ESC tab space ↵ │←↓→ │
                                  ├──────────────────────┤
                                  │  트랙패드 + L/R      │
                                  └──────────────────────┘
```

- **기본이 `PAD`** — 커버에서 키보드를 상시로 두면 스트림이 200dp 로 줄어 «보면서 친다»가 성립하지 않는다.
- **`123` 레이어** — 숫자·기호는 한 열도 못 내주므로 접었다. 라벨이 `123`↔`ABC` 로 바뀌고 켜지면 강조된다.
  레이어 1행 = 숫자 10개 · 2행 = `-` `=` `[` `]` `\` `;` `'` `` ` `` `/` `⌫` · 3행 = `⇧` `~` `!` `?` `:` `"` `<` `>` `(` `)`
- **4·5행은 펼침과 같은 구조**(왼쪽 덩어리 + 오른쪽 역T자). 자세가 바뀔 때마다 방향키 자리가
  달라지면 손이 매번 헤맨다. 계측 테스트가 ↑ 가 ↓ 바로 위에 있는지까지 잰다.

## ⌨ 키 배치 원칙

- **방향키는 역T자로 묶는다.** ↑ 를 4행 끝에 두면 ↓ 위가 아니라 ← 위에 앉아, 누를 때마다 손이 헤맨다.
  4·5행을 한 덩어리로 묶고 오른쪽에 3×2 클러스터를 세워 ↑ 가 ↓ 바로 위에 오게 했다.
- **간격은 2dp, 글자는 길이에 따라 8~12sp.** 폴드 화면에서 여백은 사치다 — 줄인 만큼 키캡이 커져
  오타가 줄고, 남은 높이는 트랙패드로 넘어간다.
- 세로 비율: 스트림 1 : 키보드 0.62 : 트랙패드 0.36 (접힘은 0.76 / 0.60)

## 🖱 트랙볼을 버리고 트랙패드로

모서리의 작은 원은 **면적이 좁아 세밀한 포인팅이 안 되고, 4·5행 키를 침범해 키보드까지 좁혔다.**
노트북식 가로 스트립으로 바꾸니 같은 높이에 면적이 몇 배가 되고, 키보드가 **전폭을 되찾았다**
(space 가 4.4 → 5.6 배폭).

**스트림에서 되는 제스처는 트랙패드에서도 된다**(스크롤 방식만 다르다).

| 손가락 | 스트림 | 트랙패드 |
|---|---|---|
| 1 | 스크롤 | **커서 이동** |
| 1 탭 | 클릭(두 번 빠르게 = 맥 더블클릭) | 좌클릭(같음) |
| 2 (같이 밀기) | 보는 영역 이동 | **스크롤** |
| 2 (벌리기·오므리기) | 확대/축소 | **확대/축소** |
| 3 (←→↑↓) | 스페이스·미션컨트롤·앱창 | **같음** |

두 손가락이 스크롤과 줌 둘 다인 건 모순처럼 보이지만 macOS 트랙패드가 정확히 그렇게 한다.
**손가락 «간격»이 변하면 줌, 간격이 그대로면 스크롤** — 제스처 시작 때 한 번만 판정하고 고정한다.
매 프레임 다시 판정하면 줌 도중 스크롤로 튀어 화면이 요동친다.
판정 중인 모드는 패드 가운데 글자로 보여준다(`TRACKPAD` / `SCROLL` / `ZOOM` / `GESTURE`).

확대 계산은 스트림과 트랙패드가 **같은 함수**(`applyZoom`)를 쓴다 — 같은 판단을 두 군데 두면 반드시 어긋난다.

바로 아래 전폭 `L`/`R` 버튼.

**판정은 `ui/Gestures.kt` 한 곳에 있다.** 전에는 같은 로직이 `MainActivity.streamGestures` 와
`Trackpad.TrackpadSurface` 두 군데에 있었고 이미 값이 어긋나 있었다(세 손가락 임계 70px vs 48px).
차이가 필요한 것은 `GestureProfile` 로 **명시해서** 가른다.

### ✅ 멀티터치는 계측 테스트로 검증한다 (`./dev.sh test`)

`adb shell input` 은 **단일 포인터만** 보낸다(`motionevent <DOWN|UP|MOVE|CANCEL> <x> <y>` — 포인터 id 가 없다).
`sendevent` 로 `/dev/input` 에 직접 쓰려면 root 가 필요한데 이 기기는 `Permission denied` 다.
그래서 두·세 손가락은 Compose 계측 테스트가 **진짜 멀티포인터 이벤트**를 흘려 검증한다
(`app/src/androidTest/.../GestureTest.kt`, 17개). 커버 키보드 치수 3개 + 독 클램프 3개까지 **총 23개**.

```bash
./dev.sh test                       # 전부
./dev.sh test kr.joonlab.foldlab.ui.GestureTest   # 한 클래스만
```

🚨 **`./gradlew connectedDebugAndroidTest` 를 쓰지 말 것.** AGP 9.4.1 + UTP 에서
**자명하게 통과하는 ASCII 테스트 하나만 돌려도** exit code 1 을 써서 `BUILD FAILED` 가 된다.
같은 실행의 XML·HTML 리포트는 `0 failures / 100% successful` 이다 — 초록을 빨강으로 보고한다.
`dev.sh test` 는 그래서 `adb shell am instrument` 를 직접 부르고 `OK (n tests)` 를 본다.

🚨 **espresso 3.5.0 은 Android 17 에서 통째로 죽는다** — `NoSuchMethodException:
android.hardware.input.InputManager.getInstance`. compose `ui-test-junit4` 가 끌어오는 게 3.5.0 이라
**테스트 16개가 전부 같은 예외**로 떨어져 로직 실패로 오진하기 딱 좋다. `espresso-core:3.7.0` 을 명시한다.

🚨 **Kotlin 은 블록 주석이 중첩된다.** KDoc 안에 슬래시+별(`/dev/input/*` 같은 경로)을 쓰면
주석이 새로 열리고, 에러는 «Unclosed comment» 로 **파일 끝**을 가리켜 원인이 안 보인다.

## 조작 방법

| 동작 | 결과 |
|---|---|
| 스트림 **탭** | 그 자리 클릭 (`TAP` 칩으로 끄면 커서만 이동) |
| 스트림 **한 손가락 드래그** | **스크롤** — 손가락 자리로 커서가 가서 그 창이 스크롤된다 |
| 스트림 **두 손가락** | 핀치 확대(1~6배) + 보는 영역 이동 |
| 스트림 **세 손가락 ←/→** | 데스크탑(스페이스) 전환 — 트랙패드와 같은 방향 |
| 스트림 **세 손가락 ↑** | 미션 컨트롤 |
| 스트림 **세 손가락 ↓** | 앱 윈도우 (App Exposé) |
| 스트림 **두 번 빠르게 탭** | 맥 **더블클릭**(단어 선택·파일 열기) |
| 키 **길게 누르기** | 연타(420ms 후 55ms 간격) — ⌫·방향키용 |
| 우하단 **트랙볼** | 커서 상대이동, 탭=좌클릭 |
| 좌하단 **L/R** | 좌·우 클릭 |

같은 동작이 칩으로도 있다(접은 커버 화면에서는 세 손가락이 사실상 불가능하다):
`◀SP` `SP▶` `MC` `앱창`

토글: `KB`(키보드 접기) `ABS`(절대좌표) `한/영` `TAP`(탭=클릭) `⌘` `opt` `⤢`(줌 순환) `↕반전`(스크롤 방향) `SYNC` `END`

## 🎙 받아쓰기 — 말한 걸 맥으로 친다 (트랙패드 오른쪽 **마이크 버튼**)

### «갤럭시 자체 음성 인식»은 없다 (실측)

이 기기에 등록된 `RecognitionService` 는 **구글 둘뿐**이다.

```
$ adb shell pm query-services --components -a android.speech.RecognitionService
com.google.android.as/...AiAiSpeechRecognitionService     ← 온디바이스
com.google.android.tts/...GoogleTTSRecognitionService      ← 기본값
```

Bixby 온디바이스 팩(`com.samsung.android.bixby.ondevice.kokr`)은 깔려 있지만 **공개
RecognitionService 를 안 내놓는다.** 삼성 키보드의 마이크도 `default_voice_input_method` 가
구글 음성 IME 라 결국 같은 엔진으로 간다. 앱에서 부를 길은 표준 `SpeechRecognizer` 하나다.

### 쓰는 법

**트랙패드 오른쪽 세로 띠**의 마이크 버튼을 탭하면 시작, 다시 탭하면 정지.
칩 줄에 섞어 두면 22dp 짜리 작은 타깃이고 다른 토글과 구별도 안 된다 —
받아쓰기는 «말하려고 손을 대는» 동작이라 손이 이미 가 있는 트랙패드 옆이 맞다.
(그 대신 `화면만` 모드에는 마이크가 없다. 트랙패드가 보이는 `KB+PAD`·`PAD` 에서 쓴다.)

| 버튼 | 뜻 |
|---|---|
| 슬레이트 + `음성` | 꺼짐 |
| 머스타드 + `기기` | 듣는 중, **온디바이스**(기기 밖으로 안 나간다) |
| 머스타드 + `망` | 듣는 중, 기본 엔진(망을 탄다) |

아이콘은 **직접 그린다**(캡슐 + U자 받침 + 스탠드). 이 폰트에 `⌥`·`⇥` 가 없어 데인 뒤로,
선 몇 개면 되는 모양은 글리프·이모지에 맡기지 않는다.

### 🚨 `Modifier.width(x).fillMaxHeight()` 는 컴포지션을 통째로 날린다

마이크 띠를 붙이면서 만난 함정. 이 순서로 쓰면 **화면이 아예 안 그려지는데
예외도 크래시 로그도 tombstone 도 없다.** 계측 테스트에만
`No compose hierarchies found in the app` 으로 나타나 원인을 엉뚱한 데서 찾게 된다.
**`Modifier.fillMaxHeight().width(x)` 로 쓴다.**

- **언어는 `한/영` 키를 따른다**(`ko-KR` / `en-US`). 듣는 도중에 바꿔도 그 언어로 다시 건다.
- **문장 단위로 보낸다.** 부분 결과는 폰 아래 **초록 띠**에만 뜬다 — 맥에 실시간으로 쓰면
  고칠 때마다 ⌫ 를 보내야 하고 그 사이 손으로 친 글자와 섞인다.
- 한 마디가 확정되면 **뒤에 공백 하나를 붙여** 보낸다. 한글 조합 중이면 먼저 확정한다.
- 앱이 배경으로 가면 마이크를 놓는다(`onStop`) — 보내지도 못하면서 듣고만 있게 된다.

띠 색: **초록 = 받아쓰는 중** · 머스타드 = 한글 조합 중 · 빨강 = 알림.

### 🚨 계측 테스트가 마이크를 쥔 채 남는다 — `ERROR_RECOGNIZER_BUSY(8)` 의 정체

실제 앱이 켜자마자 **0.5초마다 BUSY 를 20번 넘게** 받고 헛돌았다. 앱 버그가 아니었다:

```
$ adb shell dumpsys audio | grep -A2 RecordActivityMonitor
riid 19911; active? true
  session:6425 -- source client=VOICE_RECOGNITION ... pack:com.google.android.as

$ adb shell ps -A | grep foldlab
u0_a479  6952  kr.joonlab.foldlab.test     ← 끝난 줄 알았던 계측 프로세스가 살아 있다
```

**끝난 계측 프로세스가 온디바이스 인식기를 물고 있었다.** 같은 프로세스 안에서는 인식기를 둘 잡아도
충돌하지 않는다(실측) — 충돌은 **프로세스 간**이다. 게다가 이 세션은 시간이 지나도 안 풀린다
(`silenced:true` 가 될 뿐 `active? true`). 쥔 쪽 서비스를 재시작해야 놓는다:
`adb shell am force-stop com.google.android.as`.

재발 방지 둘:
1. **`dev.sh test` 가 끝나면 계측 프로세스를 force-stop 한다.** 마이크·인식기처럼 «기기에 하나뿐인»
   자원을 쓰는 테스트는 프로세스가 남으면 다음 사람이 막힌다
2. **앱도 BUSY 를 무한 재시도하지 않는다** — 3회까지 물러섰다 붙고, 그래도 안 되면 기본 엔진으로
   바꿔 보고, 그것도 안 되면 이유를 띄우고 끈다 (`DictationTest.V08`)

진단 명령:
```bash
adb shell dumpsys audio | grep -A3 '## RecordActivityMonitor'   # active? true 면 누가 쥐고 있다
adb shell ps -A | grep foldlab                                  # .test 프로세스가 남았나
./dev.sh log | grep Dictation                   # ready/partial/segment/error
```

### 🚨 끈 뒤에 오는 콜백은 «오류»가 아니다

「인식은 잘 되는데 **음성 인식 오류**라고 뜬다」의 정체.

```
16:30:22.563 stop
16:30:22.579 error=5 engine=Default listening=false   ← cancel() 에 대한 서비스의 답
```

`stop()` 의 `cancel()` 에 서비스가 `ERROR_CLIENT(5)` 로 답하는데 그걸 오류로 띄웠다 —
**잘 된 일을 실패로 보고한 것이다.** `listening` 이 false 면 `onError`·`onResults`·`onSegmentResults` 를
모두 무시한다(뒤늦게 온 결과를 맥에 써 버리는 것도 같이 막힌다). 회귀 테스트 `V11`.

### 온디바이스에 없는 언어는 «기억하고 내려받기를 건다»

이 기기는 처음에 `installed=[ko-KR]` 뿐이라 en-US 가 늘 `ERROR_LANGUAGE_NOT_SUPPORTED(13)` 였다.

- 실패한 언어를 기억해 **다음부터 헛왕복을 안 한다** —
  🚨 단 **영구로 막으면 안 된다.** 처음엔 `Set` 이었는데, 팩이 실제로 내려온 뒤
  (`installed=[en-US, ko-KR]`) 에도 앱이 다시 안 봐서 **계속 망 엔진으로 갔다**.
  60초 뒤 다시 노려보고, `ModelDownloadListener.onSuccess` 가 오면 즉시 푼다 (`V14`)
- `SpeechRecognizer.triggerModelDownload(intent)` 로 **모델을 내려받아 달라고 건다**
  (요청 뒤 그 인식기는 **바로 놓는다** — 동시 세션이 1개라 들고 있으면 정작 받아쓰기가 막힌다)
- 그 사이에는 기본 엔진으로 계속 듣는다

실제로 이 요청 뒤 en-US 가 온디바이스로 붙었다(`engine=OnDevice readyCount=1`).

### 🚨 한 번 망으로 내려가면 «영영» 망이었다

「잘 되긴 하는데 온디바이스가 아니라 망으로 나온다」의 정체.
`ensure()` 가 «인스턴스가 있으면 그대로 쓴다»여서, BUSY 한 번으로 망 엔진에 내려간 뒤에는
다시 켜도 그 인스턴스를 재사용했다. `start()` 가 «온디바이스로 쓰겠다»고 정해도 무시된 것이다.

고친 것 셋:
1. **`preferredEngine` 을 한 곳에서 정하고, `ensure()` 가 그와 다르면 갈아탄다.**
   불변식: **«쓰기로 한 엔진» == «실제 쓰는 엔진»** (`DictationTest.V13`)
2. **`retarget`(한/영 전환)이 인스턴스를 버리지 않는다** — 언어는 intent 에 실린다.
   버리고 새로 만들면 재연결 레이스로 BUSY 가 나서 **조용히 망으로 내려갔다**(실측 로그로 확인)
3. **망으로 내려가도 60초 뒤 온디바이스를 다시 노려본다** — 자리가 비면 스스로 돌아온다

### 🚨 `startListening` 은 «조용히 무시»당할 수 있다

자리가 없으면 서비스가 로그만 찍고 **ready 도 error 도 안 준다**:

```
RecognitionService: #startListening received when the service's capacity is full - ignoring this call.
```

그러면 앱은 «켜져 있다고 믿으며 아무것도 안 듣는» 상태가 된다 — 칩은 켜져 있고 띠는 조용하다.
→ 건 뒤 **2초 안에 답이 없으면 BUSY 와 같이 취급**한다(`READY_TIMEOUT_MS`).
회귀는 `V07` 이 잡는다: 6초 동안 **`onReadyForSpeech` 를 한 번이라도 받았는지**까지 본다
(`listening` 만 보면 이 상태를 놓친다 — 실제로 놓쳤었다).

### 🚨 인식기가 «ready 만 주고 안 듣는» 먹통이 된다

가장 고약한 상태. 갑자기 한국어·영어 **둘 다** 안 된다:

```
Dictation: 새 인식기 engine=OnDevice
Dictation: ready            ← 여기까지는 정상
(그 뒤 아무 콜백도 없음 — speech begin 도, partial 도, 무음일 때 오던 error=7 도 없다)
$ adb shell dumpsys audio | grep -A2 RecordActivityMonitor
   (비어 있음)               ← 녹음 세션이 아예 안 잡힌다
```

마이크 자체는 멀쩡하다 — `AudioRecord` 로 직접 재면 `recordState=3 frames=25600 peak=408`
(`MicProbeTest` 가 그걸 인식기와 **분리해서** 잰다. 이걸 못 가르면 엉뚱한 데를 고친다).
`com.google.android.as` 를 재시작하면 **즉시 정상**으로 돌아온다 — 서비스 쪽 상태 문제다.

앱이 할 일은 **알아채고 빠져나오는 것**이다. 정상이면 무음이어도 2초마다 segment/error 가 오므로,
**8초 동안 콜백이 하나도 없으면 먹통**으로 보고 엔진을 바꾼다(`WEDGE_TIMEOUT_MS`).
회귀 테스트 `V15` 는 판정 시간을 아주 짧게 줘 **탈출구가 도는지**만 본다.

**정체(2026-09-23 21차)**: `.as` 가 마이크는 열고 소리를 파이프에 붓는데 **인식 엔진(SODA)이 안 붙는다**
(`.as` 로그에 `Initialize Soda` 가 없고 `IO error writing to pipe … awaitSpace`). 그래서 `ready` 만 오고 RMS 가 0 이다.
→ 판정을 **`ready` 뒤 2초 무RMS**(`NO_AUDIO_MS`, 회귀 `V24`)로 당겼다. 건강하면 첫 RMS 가 ~0.8초에 온다.
→ **우리 테스트 스위트를 이어 돌리면 이 상태로 빠진다**(단일 테스트로는 안 난다). 그래서 `dev.sh test` 가
  끝나면 `.as` 를 재시작한다. 확인은 `./dev.sh test kr.joonlab.foldlab.input.OnDeviceProbeTest` →
  `/sdcard/Android/data/kr.joonlab.foldlab/files/ondevice-probe.txt` 의 온디바이스 `rms` 가 0 이 아닌지.

### 🚨 온디바이스 인식은 **동시 세션이 1개**다

`ERROR_RECOGNIZER_BUSY(8)` 의 정체. 서비스가 그대로 찍어 준다:

```
$ adb logcat --pid=$(adb shell pidof com.google.android.as)
AiAi: AiAiSpeechRecognitionService#getMaxConcurrentSessionsCount
RecognitionService: #startListening received when the service's capacity is full - ignoring this call.
```

그 한 자리를 누가 쥐고 있으면 **켜자마자 5~17ms 만에 BUSY** 가 난다. 자리를 잡아먹는 것 셋:

1. **끝난 계측 테스트 프로세스** — `dev.sh test` 가 이제 끝나며 force-stop 한다
2. **끈 뒤에도 인스턴스를 들고 있는 앱** — 우리 앱이 그랬다. 그렇다고 끄자마자 파괴하면 곧 다시 켤 때
   재연결 레이스로 BUSY 다 → **4초 들고 있다가 놓는다**(`IDLE_RELEASE_MS`). 짧은 재토글은 재사용,
   긴 유휴는 반납
3. 세션이 정리 안 된 채 쌓인 서비스 자신 — **서비스를 재시작하면 즉시 회복**된다(실측)

```bash
./dev.sh doctor        # 녹음 세션 · 남은 프로세스 · capacity 로그 · Dictation 로그
./dev.sh doctor fix    # 남은 계측 프로세스 + 인식 서비스 정리 (서비스는 자동으로 다시 뜬다)
```

⚠️ 자리를 못 잡으면 앱은 **기본 엔진으로 내려가고 버튼에 `망` 이라고 쓴다.** 조용히 안 넘어간다.

### 🚨 한/영을 바꿀 때 «오류»가 뜨면 안 된다

`retarget` 이 언어를 바꾸려고 `cancel()` 을 부르는데, 그때는 **켜져 있는 상태**라
「끈 뒤 콜백 무시」 가드에 안 걸렸다. 취소에 대한 `ERROR_CLIENT(5)` 가 그대로 오류로 떴다.
→ 내가 일부러 취소했으면 **바로 뒤에 오는 오류 하나는 그 답**으로 보고 무시한다 (`V16`).

### 실측 (2026-09-22, SM-F971N)

```
isRecognitionAvailable=true
isOnDeviceRecognitionAvailable=true
engine=OnDevice          ← 실제로 고른 엔진
```

🚨 **Android 11+ 는 `<queries>` 로 `android.speech.RecognitionService` 를 선언해야 한다.**
없으면 인식기가 깔려 있어도 `isRecognitionAvailable` 이 false 를 돌려줘 «이 기기엔 음성 인식이
없다»로 오진한다. `DictationTest.V01` 이 그걸 잰다.

⚠️ `SpeechRecognizer` 는 **메인 스레드에서만** 만들고 부르고 없앤다.

### 🚨 한 마디마다 인식기를 «새로 만들면» 1초도 못 버틴다

처음엔 다시 걸 때마다 `destroy()` 후 새 인식기를 만들었다. 무음 상태에서 로그가 이렇게 찍혔다:

```
50.092 start → open(OnDevice)      언어팩 ko-KR v3061 설치돼 있음
50.131 SodaAudioPusher 오디오 밀기 시작
50.695 (0.6초 뒤) end of audio → NO_SPEECH_DETECTED
50.704 error=7  (NO_MATCH)   → 150ms 뒤 재시작
50.855 open (새 인식기)
50.856 error=11 (SERVER_DISCONNECTED)  ← 여기서 죽었다
```

온디바이스 엔진(SODA)은 `blockingDisconnect`/`reconnect` 가 무거워서 그 틈에 새로 붙으면 레이스가 난다.
게다가 11 번을 «치명적»으로 분류해 꺼 버렸다 — **말할 틈조차 없었다.**

고친 것 셋:
1. **인식기 인스턴스는 하나를 재사용**하고 `startListening` 만 다시 부른다
2. **11 번은 치명적이 아니다** — 인스턴스를 버리고 700ms 쉬었다 다시 붙는다
3. **멈추는 조건을 정해 뒀다** — 연속 하드 실패 5회 또는 2분 무음이면 스스로 끈다
   (무한 재시도는 배터리만 먹는다)

### 분절 세션을 쓴다 (`EXTRA_SEGMENTED_SESSION`)

마이크를 열어 둔 채 한 마디씩 `onSegmentResults` 로 받는다. 값은 «세션이 언제 끝나는지 정하는
extra 의 이름»이다 — `EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` 를 준다.
(`EXTRA_AUDIO_SOURCE_MAX_DURATION_MILLIS` 는 **없는 상수**다.)

| | 열린 구간 | 틈 | 가동률 |
|---|---|---|---|
| 재시작 방식(250ms) | 1.0초 | 435ms | 69% |
| 분절 세션 + 50ms | **2.0초** | **282ms** | **88%** |

⚠️ **이중 전달을 막아야 한다.** 분절 세션은 `onSegmentResults` 로 주고 세션이 끝날 때
`onResults` 로 **같은 말을 또** 줄 수 있다 — 그대로 두면 맥에 두 번 찍힌다.
1.5초 창 안의 같은 말만 접는다(「네. 네.」처럼 진짜 두 번 말한 건 살린다).

⚠️ `EXTRA_SPEECH_INPUT_*_MILLIS` 계열은 **Int** 다. Long 을 넣으면 조용히 무시된다.

## ⌨ 키캡은 «지금 누르면 나올 글자»를 보여준다

전에는 각인이 늘 대문자(영문)·기본 자모(한글)라 **⇧ 를 눌러도 화면 어디에도 표시가 없었다.**
쌍시옷이 나오는데 키캡은 ㅅ 을 보여주니 지금 상태를 알 방법이 없다(2026-09-22 사용자 신고).

| | ⇧ 꺼짐 | ⇧ 켜짐 |
|---|---|---|
| 영문 | `q` `a` | `Q` `A` |
| 숫자·기호 | `1` `;` `,` | `!` `:` `<` |
| 한글 | `ㅂ` `ㅅ` | `ㅃ` `ㅆ` |
| 쌍자음 없는 한글 | `ㅁ` | `ㅁ` (2벌식에 ⇧ㅁ 은 없다) |
| 이름표가 붙은 키 | `space` `ESC` | 그대로 |

**토글 키는 색을 뒤집는다** — 꺼짐 = 슬레이트, 켜짐 = 머스타드.
전에는 모디파이어가 늘 머스타드였고 켜지면 «조금 더 밝은 머스타드»라 사실상 구별이 안 됐다.
ESC·space 처럼 토글이 아닌 강조 키는 늘 머스타드다.

**스트림 우상단 배지**에도 상태를 띄운다: `한`/`EN` + 지금 눌려 있는 모디파이어(`⇧ ^ opt ⌘`).
맥 화면을 보는 동안에는 키캡을 안 보게 되고, `PAD`·`화면만` 모드에서는 키보드가 아예 없다.

회귀 테스트 `KeycapLabelTest` 8개 — 각인은 텍스트로, 토글 색은 **픽셀을 읽어** 잰다.

## 🚨 칩의 «보이는 글자»를 식별자로 쓰지 말 것

텔레메트리 칩 목록이 «라벨 → 켜짐» 맵이었고, 눌리면 그 라벨을 도로 보내 `when` 으로 분기했다.
그런데 zone 칩은 **라벨이 상태를 따라 바뀐다**(`KB+PAD` → `PAD` → `화면만`).
한 번 누르면 라벨이 달라져 그 뒤로는 어느 분기에도 안 걸렸다 — 증상은
**«칩이 한 번만 먹고, 가로로 돌렸다 세로로 와야 다시 한 번 먹는다»**
(가로에서는 텔레메트리 바가 아예 컴포지션에서 빠졌다가 다시 생기므로 초기화된다).

→ `ChipSpec(id, label, on)` 으로 **id 와 label 을 가른다.** id 는 고정, label 만 상태를 따른다.
회귀 테스트: `TelemetryBarTest.B01` — 연속 3회 눌러 세 번 다 전환되는지 본다.

곁들여 `ToggleChip` 의 `pointerInput(Unit)` 도 `rememberUpdatedState` 로 최신 람다를 읽게 했다.
**다만 이번 버그를 고친 건 그게 아니라 id 를 가른 쪽이다**(실측으로 확인).

## 🚨 탭은 «즉시» 나가야 한다 — 더블탭을 달면 모든 클릭이 0.3초 밀린다

`detectTapGestures(onDoubleTap = …)` 을 쓰면 Compose 가 더블탭 후보를 기다리느라
**모든 단일 탭이 더블탭 대기시간(약 300ms)만큼 늦게** 나간다. 원격 조작에서 클릭이 매번
0.3초 밀리는 건 체감이 크다. 게다가 두 번째 탭이 `onTap` 으로 안 나와서
**맥에 더블클릭을 보낼 방법이 아예 없었다**(맥의 더블클릭은 «빠른 두 번의 클릭»이다).

→ 탭은 매번 즉시 내보내고, **더블클릭 판정은 deckd 가 한다**
(`InputInjector` 가 0.35초 안의 연속 클릭에 `clickState` 2·3 을 세운다 — 이미 있던 기능인데
폰이 두 번째 탭을 삼키고 있어서 쓰이지 못했다).

그 대가로 **더블탭 = 줌 리셋**은 없앴다. 전체 보기로 돌아오는 길은 텔레메트리의
`⤢` 칩이다(1 → 1.5 → 2 → 3 → 1 순환).

## 🚨 맥 제스처는 «단축키»로 보낸다 — 방향키엔 Fn 이 필요하다

트랙패드 제스처 이벤트를 합성하는 건 비공개 API 라, macOS 가 이미 갖고 있는 단축키를 쓴다.

| 동작 | 단축키 | 키코드 |
|---|---|---|
| 스페이스 왼/오른쪽 | `^←` / `^→` | 0x7B / 0x7C |
| 미션 컨트롤 | `^↑` | 0x7E |
| 앱 윈도우 | `^↓` | 0x7D |

⚠️ **Control 만으로는 안 먹는다. Fn(`0x800000`)을 같이 줘야 한다** — 실측: `^→`(Control 만) 무반응,
`^Fn→` 스페이스 전환 성공. macOS 가 `com.apple.symbolichotkeys` 에 저장해 둔 값도
`8650752 = 0x840000 = Control|Fn` 이다. 닫기는 `ESC`.

## 🚨 「한영키가 안 먹는다」의 정체 — 키코드는 맥 IME 에 걸린다

글자를 **키코드**로 보내면 맥의 입력소스(IME)가 그걸 다시 해석한다.
→ 폰은 영문 모드인데 **맥이 한글 모드면 한글 자모가 찍힌다.** 사용자 눈에는 「한영 전환이 안 먹는다」로 보인다.

**해결: 글자는 항상 유니코드로 보낸다**(`keyboardSetUnicodeString`). IME 를 우회하므로
맥이 어느 입력소스든 폰 화면에 보이는 그대로 들어간다. 실측으로 확인했다
(맥 IME 를 한국어 2벌식으로 둔 채 `abc 한글` 을 보내 그대로 도착).
⚠️ 단 **⌘C·^R 같은 조합키는 키코드여야 한다** — 유니코드로는 단축키로 해석되지 않는다.

부수 UX: **지금 어느 모드인지**가 안 보이는 것도 절반의 원인이었다(맥 화면을 보는 동안 키캡을 안 본다).
→ 스트림 우상단에 `한`/`EN` 배지를 상시 표시한다.

## 🚨 맥의 스크롤은 «포커스된 창»이 아니라 «커서 아래 창»으로 간다

스크롤 이벤트는 도착하는데 화면이 안 움직이는 증상이 여기서 나온다.
→ 드래그가 시작되면 **손가락 자리로 커서를 먼저 옮기고**(`moveAbs`) 스크롤을 보낸다.
실측: 커서를 일부러 다른 창에 둔 상태로 드래그해도 손가락 아래 창이 스크롤된다.

## 한글은 폰에서 조합한다

맥 IME 상태에 기대면 «지금 한글인지 영문인지» 를 원격에서 알 수 없어 입력이 통째로 뒤섞인다.
그래서 `input/Hangul.kt` 가 두벌식 오토마타를 돌려 **완성 음절만** 유니코드로 보낸다.
키캡 각인도 한글 모드에서 자모로 바뀐다. `⌘`·`^`·`opt` 조합일 때는 조합기를 건너뛴다(⌘C 가 문자로 새지 않게).

## 실측으로 알아낸 함정 (2026-09-22)

### 🚨 `NetworkOnMainThreadException` 은 message 가 null 이다

UI 스레드에서 `DatagramSocket.send` 를 부르면 이 예외가 난다. 그런데 **message 가 null** 이라
`catch (e: Exception) { Log.w(TAG, "send: ${e.message}") }` 는 `send: null` 만 남긴다 —
로그를 봐도 원인을 알 수 없다. 증상은 «영상은 오는데 입력만 전부 안 감».
→ 송신은 전용 스레드 + 큐로. **큐를 쓰는 또 다른 이유는 순서 보장이다**(keyDown/keyUp 이 뒤집히면 키가 눌린 채 남는다).
→ 예외 로그에는 항상 `e.javaClass.simpleName` 을 같이 찍는다.

### 🚨 람다 파라미터 이름이 멤버 함수와 겹치면 조용히 멤버가 불린다

```kotlin
fun send(build: InputBatch.() -> Unit) {
    val b = InputBatch(); b.build()   // ← 람다가 아니라 InputBatch.build() 가 불린다!
}
```
컴파일도 되고 경고도 없다. 결과는 «항상 빈 배치». 멤버 쪽을 `toBytes()` 로 바꿔 충돌 자체를 없앴다.

### `⌥`(U+2325)·`⇥`(U+21E5) 는 삼성 폰트에 없다

엉뚱한 대체 글리프로 뜬다(2026-09-22 재확인 — `⌘` 바로 옆에서 비교하면 명백하다).
`⌘`·`⇧`·`⌫`·`↵` 는 정상이므로 글리프 그대로 쓴다.

⚠️ 그렇다고 **`alt` 로 쓰면 안 된다 — 맥에는 Alt 키가 없다.** 맥 표기의 글자 **`opt`** 를 쓴다.
펼침 5행 · 커버 압축 · 플로팅 독 필수키 **세 군데가 갈리지 않게** `KeycapLabelTest.K09` 가 잰다.

### 폰 재부팅 뒤 «두 맥 다» 안 붙는다 = 폰 Tailscale 이 꺼져 있다

두 맥이 동시에 안 되면 맥 쪽보다 **폰 공통**부터 본다. 2026-09-23 실측: 재부팅 뒤 Tailscale 이 안 켜져
deckd 로그에 HELLO 가 0 건, 맥에서 `tailscale ping <폰>` timeout, `tailscale status` 에 폰이 `offline`.
→ 폰에서 Tailscale 을 켜면 즉시 붙는다. 재발 방지: 설정 → VPN → Tailscale ⚙ → **상시 사용 VPN**.
(무선 adb 도 재부팅하면 꺼진다 — `dev.sh connect` 전에 무선 디버깅을 다시 켤 것)

### 백그라운드에서는 소켓 송신이 EPERM 으로 막힌다

앱이 화면을 벗어나면 `sendto failed: EPERM (Operation not permitted)` 가 초당 쌓인다.
접속을 유지해 봐야 배터리만 먹으므로 `onStop` 에서 접고 `onStart` 에서 다시 붙는다(`DeckClient.pause/resume`).

### 키프레임이 유실되면 영영 검은 화면이다

UDP 라 큰 키프레임은 조각이 빠지기 쉽다. IDR 없이는 디코더가 시작조차 못 하는데,
델타 프레임은 계속 완성되므로 **«수신은 되는데 화면만 검은»** 상태가 된다.
→ 수신버퍼 4MB 요청(실효 8MB) + **키프레임 조각이 120ms 안에 안 차면 즉시 재요청**.
서버 쪽 버스트 페이싱과 짝을 이룬다.

### edge-to-edge 는 인셋을 직접 줘야 한다

`enableEdgeToEdge()` 만 부르면 상태바·제스처바 **아래로** 그려져 트랙볼과 하단 행이 잘린다.
루트에 `safeDrawingPadding()`.
